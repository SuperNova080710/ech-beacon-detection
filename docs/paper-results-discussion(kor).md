# 4. 연구 결과

본 연구에서는 Native Encrypted Client Hello(ECH) 환경에서 생성한 HTTPS 트래픽을 대상으로 Timing-only 탐지기와 Multi-feature 탐지기의 성능을 비교하였다. 총 200개의 실험 Trial 중 90개를 모델 학습 및 임계값 보정(Calibration)에 사용하고, 나머지 110개를 독립적인 최종 평가 집합(Held-out Test Set)으로 사용하였다.

최종 평가 집합은 Beacon 트래픽 50개와 정상 트래픽 60개로 구성하였다. 두 탐지기에는 동일한 평가 데이터를 적용하였으며, 평가 이전에 확정한 모델 구조와 판정 임계값을 변경하지 않았다.

## 4.1 전체 탐지 성능 비교

두 탐지기의 탐지 성능을 평가하기 위해 True Positive(TP), False Positive(FP), True Negative(TN), False Negative(FN)를 측정하고, 이를 바탕으로 정밀도(Precision), 재현율(Recall), F1-score, 오탐률(False Positive Rate, FPR) 및 미탐률(False Negative Rate, FNR)을 계산하였다.

**표 1. Held-out Test 집합에 대한 탐지 성능 비교**

| 평가 지표 | Timing-only | Multi-feature |
|---|---:|---:|
| TP | 50 | 50 |
| FP | 10 | 7 |
| TN | 50 | 53 |
| FN | 0 | 0 |
| Precision | 0.8333 | 0.8772 |
| Recall | 1.0000 | 1.0000 |
| F1-score | 0.9091 | 0.9346 |
| FPR | 0.1667 | 0.1167 |
| FNR | 0.0000 | 0.0000 |

*그림 1. 전체 Held-out Test 집합에서의 탐지 성능 비교 (`01-overall-performance.png`)*

실험 결과, 두 탐지기 모두 50개의 Beacon 트래픽을 탐지하여 재현율 1.0000과 미탐률 0.0000을 기록하였다. 이는 본 실험의 평가 집합에서 두 탐지기가 모든 Beacon 표본을 탐지하였음을 의미한다.

반면 정상 트래픽에 대한 분류 성능에서는 차이가 나타났다. Timing-only 탐지기는 정상 트래픽 60개 중 10개를 Beacon으로 잘못 분류한 반면, Multi-feature 탐지기는 7개를 잘못 분류하였다.

이에 따라 Multi-feature 탐지기의 정밀도는 0.8333에서 0.8772로 약 4.39%p 증가하였으며, F1-score는 0.9091에서 0.9346으로 약 2.55%p 증가하였다. 오탐률은 16.67%에서 11.67%로 5.00%p 감소하였다.

따라서 전체 평가 집합에서 Multi-feature 탐지기는 Beacon 탐지율을 추가로 높이지는 못했으나, 정상 트래픽에 대한 오탐을 감소시켜 정밀도와 F1-score를 개선한 것으로 관찰되었다.

## 4.2 Jitter 증가에 따른 Beacon 탐지 성능

Beacon 트래픽의 주기적 특성이 변할 때 탐지 성능이 어떻게 달라지는지 분석하기 위해 Jitter를 0%, 10%, 30%, 50%, 70%의 다섯 조건으로 구분하였다.

각 조건에는 최종 평가 집합에 포함된 Beacon Trial 10개를 사용하였다.

**표 2. Jitter 조건별 Beacon 탐지 결과**

| Jitter | Timing-only TP/FN | Multi-feature TP/FN | Timing-only Recall | Multi-feature Recall |
|---|---|---|---:|---:|
| 0% | 10 / 0 | 10 / 0 | 1.0000 | 1.0000 |
| 10% | 10 / 0 | 10 / 0 | 1.0000 | 1.0000 |
| 30% | 10 / 0 | 10 / 0 | 1.0000 | 1.0000 |
| 50% | 10 / 0 | 10 / 0 | 1.0000 | 1.0000 |
| 70% | 10 / 0 | 10 / 0 | 1.0000 | 1.0000 |

*그림 2. Jitter 증가에 따른 Beacon 재현율 비교 (`02-jitter-recall.png`)*

모든 Jitter 조건에서 두 탐지기의 재현율은 1.0000으로 동일하게 나타났다. 특히 실험에서 가장 높은 Jitter 조건인 70%에서도 탐지 실패가 발생하지 않았다.

이는 본 연구에서 구성한 Synthetic Beacon 트래픽과 Native ECH 실험 환경에서는 Jitter가 70%까지 증가하더라도 두 탐지기 모두 Beacon을 식별할 수 있었음을 보여준다.

그러나 두 탐지기의 재현율이 모든 조건에서 동일했으므로, Multi-feature 방식이 높은 Jitter에서 Timing-only 방식보다 재현율을 더 잘 유지한다는 우위는 확인되지 않았다.

Jitter 조건별 F1-score를 추가로 비교하기 위해 각 조건의 Beacon 10개와 동일한 정상 트래픽 60개를 결합한 조건부 평가를 수행하였다.

**표 3. Jitter 조건별 조건부 F1-score**

| Jitter | Timing-only F1 | Multi-feature F1 |
|---|---:|---:|
| 0% | 0.6667 | 0.7407 |
| 10% | 0.6667 | 0.7407 |
| 30% | 0.6667 | 0.7407 |
| 50% | 0.6667 | 0.7407 |
| 70% | 0.6667 | 0.7407 |

*그림 3. Jitter 조건별 조건부 F1-score 비교 (`03-jitter-conditional-f1.png`)*

Multi-feature 탐지기의 조건부 F1-score는 모든 Jitter 조건에서 더 높게 나타났다. 다만 이러한 차이는 Jitter 증가에 따른 Beacon 탐지율 변화 때문이 아니라, 공통 정상 트래픽 집합에서 발생한 오탐 수의 차이에서 비롯되었다.

각 조건부 평가는 동일한 정상 트래픽 60개를 반복 사용하므로, 표 3의 다섯 결과를 서로 독립적인 실험으로 간주해서는 안 된다.

## 4.3 정상 트래픽 유형별 오탐 분석

두 탐지기의 성능 차이가 발생한 원인을 구체적으로 분석하기 위해 정상 트래픽을 세 가지 유형으로 구분하여 오탐 발생 현황을 비교하였다.

평가에 사용한 정상 트래픽은 interactive-burst 24개, irregular-lognormal 18개, mixed-activity 18개로 구성되었다.

**표 4. 정상 트래픽 유형별 오탐 비교**

| 정상 트래픽 유형 | 표본 수 | Timing-only FP | Multi-feature FP |
|---|---:|---:|---:|
| interactive-burst | 24 | 0 | 0 |
| irregular-lognormal | 18 | 10 | 7 |
| mixed-activity | 18 | 0 | 0 |
| 전체 | 60 | 10 | 7 |

*그림 4. 정상 트래픽 유형별 오탐률 비교 (`04-normal-profile-fpr.png`)*

interactive-burst와 mixed-activity 유형에서는 두 탐지기 모두 오탐이 발생하지 않았다.

그러나 irregular-lognormal 유형에서는 Timing-only 탐지기가 18개 중 10개를 잘못 분류하여 55.56%의 오탐률을 기록하였다. Multi-feature 탐지기는 동일한 유형에서 7개를 잘못 분류하여 38.89%의 오탐률을 기록하였다.

또한 동일한 정상 트래픽 표본에 대한 두 탐지기의 판정 결과를 비교한 결과, 양쪽에서 모두 오탐으로 분류된 표본은 7개였고, Timing-only에서만 오탐으로 분류된 표본은 3개였다. Multi-feature에서만 새롭게 오탐으로 분류된 표본은 없었다.

따라서 본 실험에서 관찰된 Multi-feature 탐지기의 오탐 감소는 irregular-lognormal 정상 트래픽에 집중되어 있었다.

다만 해당 개선이 Packet Size, Directionality, Burst 중 특정 특징의 기여에 의해 발생했다고 단정할 수는 없다. 특징별 기여도를 확인하기 위해서는 별도의 제거 실험(Ablation Study) 또는 추가적인 특징 중요도 분석이 필요하다.

## 4.4 추론 처리 비용 비교

탐지 성능과 연산 비용 사이의 관계를 분석하기 위해 두 탐지기의 순수 추론 처리 시간을 측정하였다.

측정에는 사전에 추출된 동일한 Held-out Feature 110개와 고정된 모델 파라미터를 사용하였다. Python 3.10.12 및 Linux 6.8.0-138-generic 환경에서 `time.perf_counter_ns()`를 사용하여 시간을 측정하였다.

20회의 워밍업 이후 250회의 반복 측정을 수행하였으며, 반복마다 두 탐지기의 실행 순서를 교대하여 실행 순서에 따른 영향을 줄이고자 하였다.

**표 5. 두 탐지기의 추론 처리 비용 비교**

| 평가 지표 | Timing-only | Multi-feature |
|---|---:|---:|
| Median Batch Time (ms) | 0.080385 | 1.408802 |
| P95 Batch Time (ms) | 0.086857 | 1.447461 |
| Median per Trial (μs) | 0.730777 | 12.807295 |

*그림 5. 두 탐지기의 순수 추론 처리 시간 비교 (`05-inference-cost.png`)*

Timing-only 탐지기는 110개 Trial에 대한 중앙값 기준 처리 시간이 0.080385ms였으며, Multi-feature 탐지기는 1.408802ms였다.

Multi-feature 탐지기의 추론 처리 시간은 Timing-only 대비 약 17.53배로 나타났다.

이러한 차이는 Timing-only 방식이 단일 `iat_cv` 값과 임계값을 비교하는 반면, Multi-feature 방식은 13개 특징의 변환 및 선형 점수 계산을 수행하는 구조적 차이와 관련된다.

단, 본 측정은 PCAP 파싱, Feature 추출, 데이터 파일 입출력 및 네트워크 처리 시간을 제외한 Python 구현의 순수 추론 마이크로벤치마크이다. 따라서 측정값을 실제 운영 환경의 종단 간 탐지 지연으로 해석할 수 없다.

## 4.5 학습 및 Calibration 처리 비용 비교

두 탐지기의 모델 준비 과정에서 요구되는 처리 비용도 측정하였다.

Timing-only 탐지기는 정상 Calibration 표본 40개의 `iat_cv`를 정렬하고 임계값을 계산한다. Multi-feature 탐지기는 Calibration 표본 90개를 사용하여 800 Epoch의 L2 정규화 로지스틱 회귀 학습을 수행한 뒤 정상 표본의 점수를 이용해 임계값을 계산한다.

3회의 워밍업 이후 15회의 반복 측정을 수행하였으며, 실험 과정에서 기존 모델을 덮어쓰거나 저장된 파라미터를 변경하지 않았다.

**표 6. 모델 학습 및 Calibration 처리 비용 비교**

| 평가 지표 | Timing-only | Multi-feature |
|---|---:|---:|
| Median (ms) | 0.027777 | 199.032131 |
| P95 (ms) | 0.032999 | 216.105765 |

*그림 6. 학습 및 Calibration 처리 비용 비교 (`06-calibration-cost.png`)*

측정 결과 Multi-feature의 모델 준비 시간은 Timing-only 대비 약 7,165.36배로 나타났다.

그러나 두 탐지기는 모델 구조뿐 아니라 Calibration에 사용하는 표본 수와 수행하는 연산의 종류가 다르다. 따라서 이 결과는 동일한 연산을 수행하는 두 구현의 계산 효율 차이가 아니라, 각 탐지기의 모델 준비 절차 전체에 소요된 시간을 비교한 결과이다.

또한 Timing-only의 준비 시간이 매우 짧아 측정 시스템과 Python 실행 오버헤드에 상대적으로 민감할 수 있다.

# 5. 논의

## 5.1 연구 가설에 대한 판단

본 연구의 사전 가설은 Native ECH 환경에서 Timing, Packet Size, Directionality, Burst 특징을 결합한 Multi-feature 탐지기가 Timing-only 탐지기보다 Jitter 증가 상황에서 Beacon 탐지율을 더 높게 유지할 것이라는 것이었다.

그러나 실제 Held-out Test 결과, 두 탐지기 모두 Jitter 0~70%의 모든 조건에서 재현율 1.0000을 기록하였다.

따라서 본 실험에서는 Jitter 증가에 따른 재현율 저하가 관찰되지 않았으며, Multi-feature 탐지기의 재현율 유지 우위도 확인되지 않았다. **이에 따라 최초 가설의 핵심 주장은 이번 실험 결과로 지지되지 않는다고 판단한다.**

다만 이러한 결과가 모든 Native ECH 환경에서 Timing-only와 Multi-feature 탐지기의 재현율이 동일하다는 사실을 의미하지는 않는다. 본 실험에서 관찰되지 않은 성능 차이가 다른 Beacon 주기, Jitter 분포 또는 정상 트래픽 환경에서 나타날 가능성은 남아 있다.

## 5.2 정상 트래픽 오탐 감소의 의미

Multi-feature 탐지기는 Beacon 재현율에서 추가적인 개선을 보이지 않았으나, 정상 트래픽에 대한 오탐을 10개에서 7개로 줄였다.

특히 irregular-lognormal 유형에서 발생한 오탐이 감소했다는 점은 본 실험의 정상 트래픽 구성에서 두 탐지 방식의 구분 능력에 차이가 있었음을 보여준다.

그러나 전체 정상 표본이 60개이고, 실제 판정이 달라진 표본은 3개에 불과하다. 따라서 관찰된 개선만으로 Multi-feature의 통계적 우월성이나 실제 운영 환경에서의 일반적인 오탐 감소 효과를 확정할 수 없다.

또한 Calibration 집합에서는 두 탐지기 모두 경험적 FPR 5%를 기록하였지만, Held-out Test에서는 Timing-only 16.67%, Multi-feature 11.67%의 오탐률을 기록하였다.

이는 Calibration 집합에서 설정한 오탐률 조건이 독립적인 평가 데이터에서 그대로 유지된다는 보장이 없음을 보여준다.

## 5.3 탐지 성능과 처리 비용 사이의 절충 관계

탐지기의 실용성을 평가할 때는 분류 성능뿐 아니라 처리 비용도 함께 고려해야 한다.

본 실험에서 Multi-feature 탐지기는 Timing-only보다 오탐을 3개 줄였고 전체 F1-score를 약 2.55%p 높였다.

반면 추론 처리 시간은 약 17.53배 증가하였으며, 모델 준비 시간은 약 7,165.36배 증가하였다.

따라서 Multi-feature 방식은 본 실험에서 추가적인 계산 비용을 요구하는 대신 정상 트래픽에 대한 오탐을 일부 줄이는 특성을 나타냈다.

다만 상대적인 처리 시간 증가율이 크다는 사실만으로 실제 운영에 부적합하다고 결론 내릴 수는 없다. 추론 과정의 절대 처리 시간은 단일 Trial 기준 수십 마이크로초 미만이었으며, 실제 운영 가능성은 처리해야 하는 트래픽 규모, 동시성, 처리 장치 및 시스템 요구사항에 따라 달라진다.

본 연구에서는 두 방식의 상대적인 연산 비용 차이를 확인하였지만, 실제 운영 환경에서의 자원 사용량이나 시스템 처리량까지 검증하지는 않았다.

## 5.4 Native ECH 환경에서의 탐지 가능성과 해석 범위

본 연구는 Native ECH가 적용된 HTTPS 통신에서도 암호화된 애플리케이션 내용 대신 Flow 기반 메타데이터를 활용하여 Beacon 탐지를 수행할 수 있음을 제한된 실험 환경에서 확인하였다.

이는 TLS 애플리케이션 데이터의 복호화 없이도 패킷 크기, 전송 방향 및 Flow 발생 시각 등의 정보를 탐지에 활용할 수 있음을 보여준다.

다만 ECH 자체의 효과와 Beacon 탐지 성능의 관계를 분리하여 평가한 실험은 아니다. 따라서 본 연구 결과만으로 ECH 적용 여부가 탐지 정확도를 향상하거나 저하시킨다고 주장할 수는 없다.

본 연구의 실험적 기여는 Native ECH 환경에서 두 가지 경량 탐지 방식을 동일한 데이터와 평가 절차로 비교하고, 탐지 성능과 처리 비용의 차이를 정량적으로 제시한 데 있다.

# 6. 연구의 한계

본 연구에는 다음과 같은 한계가 존재한다.

첫째, 실험 데이터는 실제 악성코드의 Command and Control(C2) 통신이 아니라 통제된 환경에서 생성한 Synthetic HTTPS Beacon 트래픽이다. 따라서 실제 악성코드의 통신 행위와 기업 네트워크의 복잡한 트래픽 특성을 충분히 반영하지 못한다.

둘째, Native ECH 실험은 제한된 단일 테스트 환경에서 수행되었다. 다양한 운영체제, 네트워크 지연, 패킷 손실, 서버 구현 및 동시 접속 조건을 포함하지 않았다.

셋째, Beacon의 기준 주기는 1.0초로 고정하였으며, Jitter는 0~70%의 다섯 수준에서만 평가하였다. 서로 다른 기준 주기나 더 복잡한 시간 변동에 대한 탐지 성능은 확인하지 않았다.

넷째, 최종 평가에서 각 Jitter 조건의 Beacon 표본은 10개에 불과하였다. 또한 정상 트래픽은 세 가지 Synthetic 프로필로 제한되었다. 따라서 실제 네트워크 환경에서의 재현율 및 오탐률을 일반화하기에는 충분하지 않다.

다섯째, Multi-feature 방식에서 관찰된 오탐 감소가 어떤 특징 조합에서 비롯되었는지 직접 검증하지 않았다. 개별 특징의 기여도를 정량적으로 평가하기 위해서는 추가적인 Ablation Study가 필요하다.

여섯째, 두 탐지기의 성능 차이에 대한 통계적 유의성 검증이나 신뢰구간 분석은 수행하지 않았다. 따라서 관측된 오탐 감소를 모집단 수준의 우월성으로 확대 해석하지 않는다.

일곱째, 처리 비용 측정은 Python 단일 실행 환경에서 이루어진 마이크로벤치마크이며, 개별 반복 측정 시간 대신 요약 통계만 보존하였다. 실제 패킷 수집부터 최종 탐지 결과까지의 종단 간 지연, CPU·메모리 사용량 및 시스템 처리량은 평가하지 않았다.

향후 연구에서는 다양한 Beacon 주기, 추가적인 정상 트래픽 유형, 실제 네트워크 캡처 및 독립적인 외부 데이터셋을 활용한 검증이 필요하다. 또한 특징 제거 실험과 통계적 불확실성 분석을 통해 Multi-feature 방식의 개선 원인과 일반화 가능성을 추가로 검토할 수 있다.

# 7. 결론

본 연구에서는 Native ECH 환경에서 생성한 Synthetic HTTPS Beacon 트래픽을 대상으로 Timing-only 탐지기와 경량 Multi-feature 탐지기의 탐지 성능 및 처리 비용을 비교하였다.

총 200개의 실험 Trial을 수집하고, 사전에 확정한 분할 기준에 따라 90개를 Calibration에, 110개를 최종 Held-out Test에 사용하였다.

실험 결과, 두 탐지기 모두 Jitter 0~70%의 모든 조건에서 Beacon 재현율 100%를 기록하였다. 따라서 Multi-feature 탐지기가 Jitter 증가 상황에서 Timing-only 탐지기보다 재현율을 더 높게 유지할 것이라는 최초 가설은 이번 실험에서 지지되지 않았다.

반면 Multi-feature 탐지기는 정상 트래픽에 대한 오탐을 10개에서 7개로 줄였으며, 이에 따라 F1-score가 0.9091에서 0.9346으로 증가하고 FPR은 16.67%에서 11.67%로 감소하였다.

처리 비용 측면에서는 Multi-feature 탐지기의 순수 추론 시간이 Timing-only 대비 약 17.53배, 모델 준비 시간이 약 7,165.36배로 측정되었다.

종합하면 본 실험에서 Multi-feature 탐지기는 Beacon 재현율의 추가적인 향상 없이 정상 트래픽 오탐을 일부 감소시켰으나, 그 대가로 더 높은 계산 비용을 요구하였다.

따라서 본 연구의 결과는 Multi-feature 방식의 일방적인 우월성을 입증하기보다는, **Native ECH 환경에서 경량 Beacon 탐지기를 설계할 때 오탐 감소 효과와 연산 비용을 함께 고려해야 한다는 점**을 보여준다.

이러한 결과는 제한된 Synthetic 실험 조건에서 관찰된 것으로, 실제 악성 C2 트래픽에 대한 일반화 성능을 확정하는 근거로 사용해서는 안 된다.
